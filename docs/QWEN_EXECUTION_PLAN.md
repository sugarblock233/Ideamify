原因：loadUpdates 提升全局 revision，却保留旧 draft/draftBase；saveDraft 使用全局 revision。`rebaseDraft` 已存在，但没有可点击的 UI。

定位：`frontend/src/workspace/Workspace.tsx` 的 loadUpdates/commit/saveDraft/rebaseDraft，`SidePanel.tsx`。

执行要求：

- [ ] 草稿保存读取时的基线内容和基线 revision，其他界面刷新不能悄悄提升草稿基线。
- [ ] 干净的详情在主动载入更新后显示新内容；脏草稿保留，明确显示“本地草稿／服务器新版”。

- [ ] 冲突处理后再发生新提交，仍然需要再次检查版本，不能把重排草稿当成锁。
- [ ] 任意操作导致当前节点详情重载时，都不能丢草稿或绕过基线；检查移动、改关联、切换项目、退出、重复点当前节点等入口。
- [ ] 使用节点完整响应自带的 project_revision，避免把内容读取后另一次 project 查询的更高版本误当内容基线。

验收至少包括：同字段冲突、不相交字段变化、无草稿更新、冲突后再次被他人更新、取消离开后草稿不丢失。后端原有项目级版本锁继续有效。

### A04 · P2：context 字符预算、遗漏标记与查询优先级

实际测量（Unicode 字符、紧凑 JSON 序列化）：4000 预算返回 4347 字符；12000 返回 12314；多关联 focus 的 50000 返回 50381。大量条目被省略时 truncated 仍为 false。`q=1099` 的唯一命中在 12000 预算下被一般概览挤掉。

定位：`backend/app/context.py`。

执行要求：

- [ ] 最终输出连同 warnings、omitted_counts、continuations 一起计入 max_chars；返回前再次保证总预算成立。
- [ ] 字段截断或整条省略都设置一致的 truncated 标记，计数与实际返回对应。
- [ ] 必要项目/焦点/祖先骨架放不下时返回明确的 CONTEXT_BUDGET_TOO_SMALL 和所需下限。
- [ ] 有 q 时，在必要骨架之后优先返回关键词相关内容；有 focus 时保留反证、依赖、失败条件和必要上下文的优先级。
- [ ] focus 的近期变化应优先与当前问题相关，不让无关分支更新挤占预算。

### A05 · P2：CLI 缺省 ID/版本造成不安全重试

现象：同一个不带 request_id/expected_revision 的 update 文件，两次 `commit ... --auto-rev` 分别生成不同请求身份，两个提交都成功；文件未保存生成的字段。409 的 stderr 在 JSON 后追加说明，整段无法直接 JSON 解析。

定位：`tools/researchmap.py`、`docs/AI_USAGE.md`、`docs/DECISIONS.md`。

执行要求：

- [ ] 一次逻辑提交必须有稳定的完整请求体，预检查、正式提交和网络重试共用相同身份及读取基线。
- [ ] 最简单可靠的默认方案是：commit 要求完整 request_id/expected_revision，缺失时给出可操作错误。若保留自动准备能力，必须显式生成并保存到文件，不能仅在内存填充。
- [ ] 保留现有常用命令兼容性，`--auto-rev` 不能成为静默绕过冲突的默认补救。需要刷新基线时先重读内容，再显式准备新的请求内容。
- [ ] 区分请求已成功但回执丢失、409 从未写入、同 ID 改内容三种情况；已成功请求重试不得更改哈希字段。
- [ ] 成功 stdout 提供机器可解析输出；失败采用稳定 JSON 错误结构和非零退出码，说明放入结构字段，不混入不可解析的尾部文字。
- [ ] 凭证从环境变量输入，不要求令牌出现在命令参数、提交文件、URL 或日志中。

验收：完整请求成功重试只有一个 commit；方便模式不得重复写入；dry-run 后遇到并发变化会拒绝而非刷新版本绕过；409 和网络错误能被自动化解析。

### G02：英文 Git 提交、PR 与发布摘要

用户说的“推送摘要”主要落实到 Git commit message、PR 标题/说明和 Release notes；`git push` 本身不是另一套单独维护的摘要。

| 内容 | 本仓库约定 |
| --- | --- |
| Git commit subject | 英文，简洁，说明改动目的 |
| Git commit body | 英文优先，补充原因/影响/验证；必要时附中文说明 |
| PR 标题、主要说明 | 英文优先，可附中文摘要 |
| CHANGELOG、Release notes | 英文主条目，可附中文摘要 |
| 面向维护者的开发文档、代码标识符 | 英文优先；保留有价值的现有中文，不机械翻译所有注释 |
| Issue、讨论和用户求助 | 接受英文或中文，不因语言拒绝贡献 |
| 产品 UI、用户研究文本、应用内 Commit.summary | 保持用户选择；**不应用 Git 提交的英文规则** |

采用轻量 Conventional Commits：`type(scope): short description`。使用 fix、feat、docs、test、ci、build、refactor、perf、chore 等，scope 可选。该规范定义结构和变更含义，本项目另外约定摘要用英文。[Conventional Commits 规范](https://www.conventionalcommits.org/en/v1.0.0/)

示例（按实际改动选择，不照抄无关标题）：

```text
fix(editor): preserve draft revisions during refresh
fix(onboarding): allow creating the first project
fix(context): include metadata in character budgets
fix(cli): preserve request identity across retries
fix(canvas): collapse deep branches on first load
docs(readme): add English and Chinese getting-started guides
ci: verify frontend, backend, and container workflows
```

- [ ] 一组相关变化一个提交；功能修复、文档、纯格式化合理分开，不提交“update”“fix bugs”“完成”等模糊标题。
- [ ] subject 推荐约 72 字符内，不强行拆坏术语；正文解释需要知道的原因，不粘贴整个开发日志。
- [ ] 破坏已有 API/CLI 行为时明确说明迁移与兼容，并使用 breaking-change 标记；不借此擅自改写原规格。
- [ ] 新分支使用英文小写和连字符，默认沿用现有 main，不引入 develop/release 等复杂常驻分支。
- [ ] 不为把旧中文提交改成英文而重写已共享历史、force push 或修改用户 Git 身份。
- [ ] 在 CONTRIBUTING 与 AGENTS 中写明约定。可对 PR 标题做轻量校验，优先兼容 squash merge，不要求普通贡献者安装一整套提交工具。

- [ ] 不自动创建演示公网服务；发布脱敏静态截图就能满足本轮展示需求。

### G09：保持仓库维护轻量

- [ ] 根 README、CONTRIBUTING、AGENTS 之间职责明确，不复制一整套互相漂移的说明。
- [ ] 修复文档与对应功能在同一批改动中更新，重大研究语义的决定简述在 DECISIONS。
- [ ] 为 bug、enhancement、documentation、question、good first issue、help wanted 等标签准备简洁用途说明；远端存在时复用，不批量制造空 Issue。
- [ ] 没有真实维护者列表时不编造团队；致谢如实写 AI 辅助，Git 作者使用现有真实配置，不把模型冒充真人贡献者。
- [ ] 给出一个简单的维护节奏：依赖 PR 按周查看；发布前走清单；功能变化同步双语文档；安全问题通过私密渠道处理。不要承诺用户尚未接受的响应时限。

把下表整理到最终交付的“待所有者处理”部分。先完成可以落地的代码、文档和验证。不能将本地文件的完成等同于远端配置已生效。

## 8. 实施顺序与验证要求

### 分批执行

1. **基线与数据隔离**：检查 HEAD、工作区和现有规则；运行相关基线检查；准备可重复的合成数据与临时测试环境。
2. **正确性和阻塞**：A01/A02/A03、D01；补会失败的场景测试再验证修复。
3. **AI 与交互完整性**：A04–A09、B01–B06；按读→写→冲突→回看历史的完整流程检查。
4. **部署和仓库基础**：D02/D03、G01–G09；代码修复先稳定，截图和命令随最终行为更新。
5. **复验与交付**：完成以下矩阵与 B07，准备英文提交/PR/Release 摘要和 G10 的具体待办。

不要把所有改动塞入一个大提交，也不要仅完成 README 就宣布开源规范化完成。常规实现选择自行决定并记录，遇到会改变产品边界、授权或科学语义的重要选择再提出。

状态只能准确使用：**已修复且验证／已实现未验证／待所有者决定／待远端权限／未完成**。本模板的横线是要求填写的状态表，不得原样当作完成结果。

## 10. 本轮暂不引入

自动发布 npm/PyPI 包、复杂分支模型、CLA 系统、维护者组织权限、自动关闭 Issue 的机器人、自动合并所有依赖升级、GitHub Pages 文档站、公开在线演示站、付费代码质量平台、全量 UI 国际化、CITATION.cff/DOI 自动发布、复杂自动发版或多平台镜像矩阵。

这些能力可以在真实需要出现后另行评估。没有准确作者/引用信息时不造科研引用；没有发布授权时不推送任何公共制品。本轮的重点是：功能可靠、说明准确、英文与中文入口清楚、改动可审阅、测试能持续运行。
