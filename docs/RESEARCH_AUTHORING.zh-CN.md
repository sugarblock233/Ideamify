# 研究内容编写指南：先建路线，再沿问题深入

[English](RESEARCH_AUTHORING.md) · [AI 读写协议](AI_USAGE.zh-CN.md) · [开始使用](GETTING_STARTED.zh-CN.md) · [文档目录](README.md)

本指南可用于当前版本，使用现有节点、字段和 CLI，不依赖尚未实现的研究阅读界面。未来界面方案见 [改造交付书](RESEARCH_MAP_REDESIGN.zh-CN.md)。下文所有案例均为**合成示例**。

目标是帮助未必亲自写代码、跑实验的研究者回答：我们在解决什么、为什么走这条路线、目前凭什么这样判断、下一步应该弄清什么。AI 整理的成果应当是一份可读的研究结构。

## 1. 开始前先确定交付范围

区分本次任务属于哪种情况：首次建图、整理旧资料、接续某条路线，还是只补充一项发现。使用用户已经给出的授权和约束；“整理实验代码”本身不授权执行实验，“推荐路线”也不自动授权写入或重排已有地图。

先读项目目标和全局路线，再聚焦相关分支。读取示例（PID/NID 是占位符，执行前替换；连接配置见 AI_USAGE）：

```bash
python3 tools/researchmap.py project PID
python3 tools/researchmap.py context PID --format json
python3 tools/researchmap.py graph PID
python3 tools/researchmap.py context PID --focus NID --format json
python3 tools/researchmap.py node PID NID
python3 tools/researchmap.py relations PID NID
```

`graph` 提供 parent_id 和顺序，适合识别路线与祖先；它不是节点全文。当前 `context` 不包含 rationale、details_md 和完整证据，必须用 `node` 补读焦点、相关路线及关键来源。关键词搜索、未返回记录或关系第一页都不代表全部历史。遵循 omitted_counts、continuations 和分页信息，核对范围后再下结论。

先给出一段短理解：项目目标、已有路线、当前聚焦问题、已知结论与缺口。普通信息不足可标注假设继续整理；只有会改变主要研究方向的缺失信息才需要向研究者询问。不要每增加一个节点都要求确认。

## 2. 先找大的路径

首次建图或重组前，先形成一份路线草案。已有合理结构时沿用它，不为遵守流程重新建图。

| 内容 | 必须说明 |
| --- | --- |
| 项目问题 | 想解释或改善的现象是什么，成功如何判断，哪些约束不可忽略 |
| 主要路线 | 每条路线针对哪种机制、瓶颈或解释，为什么与其他路线不同 |
| 选择依据 | 来自已有资料、观察还是待检验推测；不要把覆盖所有可能性当作目标 |
| 关键子问题 | 哪个问题值得先弄清，它会如何影响路线选择 |
| 继续/停止条件 | 什么观察会让我们继续、调整、暂停或转向；未知时明确写待定 |

一般先给 2–5 条有依据的大路线；只有一条合理路线也可以，不补造凑数。每条路线先拆少量可区分的子问题，再深入当前关注的一个。不要一次把所有路线补到相同深度。

合成示例：项目“提高检索证据覆盖率，同时控制无关结果”。

- 路线 A：改善查询表达，检查同义词和概念表达造成的漏检。
- 路线 B：改善结果筛选，检查候选排序如何影响有效证据。
- 路线 C：检查评价集合，确认覆盖率指标是否真的反映研究需要。

“预处理代码”“实验脚本”“结果文件夹”可作为资料类别，但通常不能直接担任一级研究路线，因为读者仍不知道它们在回答什么问题。

## 3. 用问题组织归属，用理由连接思路

一级路线是 `parent_id=null` 的 question/idea。往下可以是子问题、假设、方法比较、尝试、发现或新的问题，使用现有四种 kind：

| 内容角色 | 常用 kind | 写法 |
| --- | --- | --- |
| 路线或子问题 | question | “哪些漏检来自术语差异？” |
| 假设或方法建议 | idea | “受控同义词扩展可能减少术语漏检” |
| 有明确区分目的的探索 | attempt | “固定集合上比较原查询与受控扩展” |
| 可以独立引用的认识 | finding | “在合成对照中，扩展同时增加相关与无关命中” |

**主树只表示主要归属。** 如果新问题主要在研究“触发条件”，可以把它放在该问题的上位路线下，再用 `motivates` 连接启发它的失败尝试，不必把所有后续都挤成一条父子链。

| 关系 | source → target 的含义 |
| --- | --- |
| motivates | 先前问题或发现 → 由它启发的新问题/方法 |
| supports | 提供证据的节点 → 被支持的有限陈述 |
| contradicts | 提供反证的节点 → 被质疑的有限陈述 |
| depends_on | 需要某前提的工作 → 它依赖的前提 |
| related | 相关但尚不能说明更强关系；无向 |

每个 reason 写明具体联系，例如“扩展带来的噪声使我们需要研究何时触发扩展”。“有关”“后续实验”不足以交代承接。只在内容有依据时创建关系，不能为让图看起来连贯而补造因果。

有实质进展的深入示例：

```text
改善查询表达
  └─ 哪些漏检来自术语差异？
       └─ 受控同义词扩展能否补回证据？
            └─ 固定集合上的对照尝试
                 └─ 哪类查询产生了额外噪声？
                      └─ 多义词是否使扩展词偏离原意？
                           └─ 限制词义范围是否能保留收益？（待验证）
```

这是一个可选的归属结构，每次转折还须在 rationale/decision 或真实关系中说明依据。没有实验或分析来源时，只能写待验证问题；不要沿着示例编造结果。深度不是配额，研究可以停在第 2 层，也可以在充分依据下深入更多层；当前结构上限为 64。

## 4. 一个节点应该让人读懂什么

| 字段 | 内容要求 |
| --- | --- |
| title（最多 80 字符） | 一个问题、方法差异或有限认识；避免只有脚本名、编号和参数 |
| summary（最多 280 字符） | 不读代码也能懂的一句话：研究目的/变化、当前认识、关键限制 |
| rationale（最多 2000 字符） | 为什么从上一步走到这里，这一步要区分什么解释，采用什么思路 |
| finding（最多 2000 字符） | 直接观察，或明确“尚无结果/未确认执行”；与机制解释分开 |
| decision（最多 2000 字符） | 当前解释、取舍与下一步；标注推测及判断改变的条件 |
| scope（最多 1000 字符） | 实际或拟议的适用条件，说明两者的区别和未覆盖范围 |
| details_md | 方法细节、来源说明、代码用途、比较过程、运行与复现信息 |
| evidence | 支持具体陈述的资料定位；label 表明用途，note 表明来源及未核验部分 |

技术正文可以使用以下结构，但无需对每个节点机械填写所有标题，也不要把它当成应用会解析的字段协议：

```markdown
## 要回答的问题
这个方法或材料要帮助区分什么？
## 方法与比较
输入、输出、对照和成功判断；尚未执行的部分明确标注。
## 资料与执行情况
看过什么来源，能确认到什么程度，还缺什么。
## 观察与解释
原始观察是什么，解释有哪些竞争可能。
## 下一步与改变判断的条件
最值得继续弄清的问题，以及相应依据。
```

不把长日志塞进摘要，不复制全部代码到节点。保留能回答研究问题的说明与精确引用。

## 5. 面对实验代码时，先核对能知道什么

| 资料状态 | 正确的记录方式 |
| --- | --- |
| 只有方案 | 说明假设与验证设计，通常 unexplored |
| 有代码，未发现执行依据 | “已实现 X，用于检验 Y；未确认执行，效果未知”；研究效果仍 unexplored，若实际在推进该探索可 in_progress |
| 有执行日志但缺有效指标或对照 | 描述来源记录的执行和缺口，结论通常 inconclusive |
| 有初步积极观察 | 说明来源、范围和局限，必要时 promising |
| 有足够支持有限判断的证据 | supported/not_supported，并填写 scope、finding、decision 和 evidence |
| 历史回忆、无法打开的引用 | 明确“历史回忆/来源未核验”，不写成亲自核实的事实 |

这些资料状态不是新的 API 枚举。脚本存在不等于跑过；运行成功不等于方法有效；AI 说“完成”不等于有结果。对代码行为的判断可以引用代码，但不能据此把效果假设标绿。

不要为了补齐记录擅自运行代码。需要执行才能回答的问题，写为下一步并按用户的实验任务授权处理。环境错误一般是 inconclusive，不足以否定研究方向。纯理论推导或文献分析不必伪装成实验；据其实际论据记录。

合成的改写前后：

| 原记录 | 改写为 |
| --- | --- |
| title: `expand_v3.py`；summary: 完成实验代码 | title: 受控扩展能否减少术语漏检？summary: 已实现受控同义词扩展，用于比较覆盖与噪声；尚无可核验运行记录，效果未知。 |
| title: run_07；summary: 效果不好 | title: 扩展增加覆盖时是否引入噪声？summary: 在该合成对照范围内，相关命中增加，但无关命中也增加；下一步检查哪些查询需要限制扩展。只有确有来源时才能这样写。 |

对代码引用应补充：用途、输入输出、相对其他方法的变化、对应研究问题，以及可确认的执行情况。路径只是定位信息，应用不会打开或执行它。

## 6. 每次更新维护研究承接

一次有价值的增量，先回答三个问题：为什么做这一步？实际获得什么认识？它怎样影响下一步？

- 同一假设、同一方法下补充结果或纠错，通常更新原节点；参数扫描通常用一张结果表。
- 新的机制假设、实质方法变化或不同适用条件，建立新节点并保留前一个结果。
- 独立发现需要多处引用时，用 finding 节点和真实关系共享，避免复制成多个独立证据。
- 新观察改变某条路线的判断时，检查该路线 summary/decision；在任务授权内更新受影响祖先，不动无关分支。
- 结论没有变化时不重复改写路线综述；路线状态由其自身陈述和证据决定，不从子节点颜色计算。
- 有负结果就保留范围、证据和停止/继续理由；“暂停”写在 decision，归档不等于失败。

路线综述推荐写成：“这条路线在解决 X；目前在条件 Y 下知道 Z，依据是节点/材料 A；仍缺 B，因此下一步 C。”无法填的部分如实标注未知。

## 7. 整理旧项目的方法

先做只读清点：原节点 ID、来源、可读含义、能确认的执行情况、建议路线和不确定项。先做一条代表性路线的整理草案，检查读者能否理解，再在授权范围内扩展。

已有节点的 ID、历史、证据、版本归属和人工备注应保留。通过 node.move 调整归属，通过 node.update 改写题目/摘要和必要说明；不要为得到干净的图删掉原图再导入。缺少来源的资料保留为待核实，不从文件名倒推实验结果。

编写任务已授权结构整理时，常规归属调整无需逐条询问；涉及超出授权范围的路线取舍、批量归档或真实数据库访问才停下明确边界。开发 AI 在本仓库只能使用 scratch 数据，不能把真实研究内容提交进仓库。

## 8. 提交与读回

仍使用 [AI_USAGE](AI_USAGE.zh-CN.md) 的完整协议：先读取基线，准备稳定请求体，dry-run，再正式提交，再读回。

1. 为每条拟新增内容核对父路线、研究意义和来源；先建父节点，再建子节点，关系放端点之后。
2. 在请求中显式填写从已读内容得到的 expected_revision。CLI 自动补当前 revision 不能代替你读懂当前版本；多次读取跨版本时先重新核对受影响内容。
3. 每个 commit 一个可理解的研究增量，最多 100 operations；必要的节点、关系及路线综述修订可以原子提交。更大重组拆为每批都自洽的小变化。
4. dry-run 只校验结构和填写完整性，不能证明研究内容真实或易读。网络重试使用同一请求身份；409 后重读、合并，不能只刷新 revision 强行覆盖。
5. 正式提交后读回修改的节点和关系，核对方向、父级、范围、状态及摘要。使用当前地图可见布局检查组织结果；没检查浏览器就不要声称视觉已验收。

编写质量核对：顶层是否是研究路线；每个新节点是否有独立意义；前因与下一步是否有来源；代码是否被误当结果；未知和负结果是否保留；不读代码能否解释本次变化。无法满足的地方明确列为待补信息。

## 9. 给研究负责人的交接

默认用简短自然语言交接以下内容，必要时附节点 ID 或深链接：

1. **当前路线**：我们在回答什么，为什么先走这里。
2. **新增认识**：实际得到了什么，证据支持到什么范围；未执行就明确说明。
3. **路线影响**：什么判断改变了，哪些备选仍然成立。
4. **下一步**：最值得弄清的一个问题，及其选择依据。
5. **需要研究者决定的事**：只列影响方向、成本或授权的重要问题；没有就省略。

不要只交付“新增 18 个节点、整理 12 个脚本”。节点变化清单和 export 是追溯材料，不能代替研究说明。

## 10. 可直接交给内容整理 AI 的指令

> 阅读 docs/RESEARCH_AUTHORING.zh-CN.md 和 docs/AI_USAGE.zh-CN.md，在本次任务授权范围内整理 PROJECT_ID 的科研地图。
>
> 先读项目目标、全局路线与当前分支，说明主要问题和资料缺口。先找有依据的大路线，再在路线下拆子问题，优先深入当前问题；沿用合理的已有结构，不按脚本、时间和运行编号建顶层目录，也不凑节点数量或深度。
>
> 每个节点用非执行者能理解的标题和摘要，说明为什么做、观察到什么、如何影响下一步；代码与运行细节放详情和证据。区分设想、实现、执行、观察与解释，没有运行依据就写未知。本任务不自动授权执行实验。
>
> 主树只表达归属；用有理由的关系说明研究承接，保留负结果、人工备注、来源、节点 ID 与历史。只在新认识确实改变路线时更新相关综述，不自动传播状态。遵守读取基线、dry-run、幂等提交、冲突处理和读回规则。
>
> 最后交接当前路线、新增认识、路线影响与一个有依据的下一步，明确尚未验证的部分。若本次只要求规划，则交付路线草案和建议修改清单，不提交写入。
