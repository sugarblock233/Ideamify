# ResearchMap v0.1 — 轻量科研演化地图开发规格

版本：0.1 · 设计日期：2026-09-13  
性质：交给开发 AI 的产品与工程规格，不是已实现的软件。  
暂用名：ResearchMap。名称不构成商标或可用域名判断。

## 0. 一句话定义与范围

做一个可部署在服务器上的轻量 Web 应用，让研究者和不同 AI 共同维护同一份科研演化地图：从问题分出路线，记录有价值的尝试、观察、成功、失败和下一步；主图简洁，详情按需查看，过去的探索能够被后来的人和 AI 继承。

**核心设计：数据允许跨分支关联；排版只依据主树；跨分支连线按需显示。**

本规格中的“必须”是 v0.1 验收项；“以后再做”不属于本轮开发。缺少小细节时采用最简单且不破坏下述约束的实现，并记录选择，不要自行扩建产品。

### 明确做什么

浏览器中的项目地图、节点编辑、折叠与定位、跨分支关系、短摘要与详情、证据引用、变更历史、AI 读取上下文与批量增量提交、单机服务器部署、导出与备份。

### 明确不做什么

不做自动科研执行、GPU/Slurm 管理、训练监控、自动读论文、内置聊天或模型调用、向量数据库、图数据库、实时多人光标、组织权限体系、移动端专门适配、自由白板、复杂图形编辑、时间轴、全局关系网布局、自动从旧对话推导完整历史、MCP 服务。

v0.1 的使用者是**一个研究者和其信任的若干 AI 工具**。可以有多个项目，但不是公开多租户平台。没有模型 API Key 也应能运行全部核心功能。

### 需要承认的边界

应用不会自动知道外部 AI 做过什么。AI 必须按记录协议提交变化。应用可以检查结构、证据引用是否填写，不能保证研究结论正确，也不能自行证明引用文件真实存在。第一版能被命令行/HTTP 工具使用；不等于所有网页聊天产品已经自动接入。

### 0.2 规划增量（2026-09-14，A+B 批次落地后的增补）

本节是 v0.1 规格的增量修订，原文各节语义在增补点之外保持不变：

## 1. 典型使用闭环

1. 人创建项目，写一段研究目标，建立几条初始路线。
2. 新 AI 读取项目概况，再读取相关节点、祖先和关联节点，查看既往失败的条件。
3. AI 在应用之外调研、写代码或实验。
4. 形成独立发现或决策后，提交一个小的增量：新增/更新节点、更新状态、补充证据或建立关联。
5. 人打开地图，看到哪些地方发生变化；点开节点可以知道为什么改变，而不是翻完整日志。
6. 换 AI 或换设备后，从同一份记录继续。

成功标准不是“保存了多少字”，而是能快速回答：研究什么？走过哪些路线？为什么停止或继续？证据在哪里？下一步尚未解决什么？

## 2. 图的结构：主树 + 关联层

### 2.1 主树只表示组织归属

每个节点有且只有一个 `parent_id`，或者 `null` 表示项目下的一级节点。项目在画布上有一个虚拟根，其 ID 采用 `project:<project_uuid>`；虚拟根不是普通 Node，不可被关联引用。

同一个项目可以有多个一级节点，画布将它们连接到虚拟根。

主树回答“这个节点主要属于哪条路线”，不自动断言逻辑蕴含、因果关系或唯一来源。节点可以属于 A 路线，同时与 B、C 路线产生关联，不复制三份内容。

主树必须无环。节点不能成为自己的父节点，不能移动到自己的后代下；父节点必须在同一项目中且未归档。主树最大深度暂定为 64，超出时给出明确校验错误。

### 2.2 跨分支关系独立存储

关系的两个端点可以处于任意分支，也可以处于同一分支。第一版只提供五种：

| API 类型 | 中文含义 | 方向定义 |
| --- | --- | --- |
| `related` | 相关 | 无向；只表示有关联 |
| `motivates` | 启发 | A 的发现/问题启发了 B |
| `supports` | 支持 | A 提供的证据支持 B 的陈述 |
| `contradicts` | 反对/不支持 | A 提供的证据不支持 B 的陈述 |
| `depends_on` | 依赖 | A 的开展依赖 B |

关系必须带简短 `reason`，不能只写一个没有解释的箭头。方向以本表为准，不额外生成 `supported_by` 等反向同义类型。

跨关系允许成环，不能使用主树的无环校验来拒绝合法关联。禁止自关联、跨项目关联。`related` 按两个 UUID 的字典序规范化后去重，其余类型按有向三元组 `(source_id, target_id, kind)` 去重。不同类型可以连接同一对节点。

关系是使用者登记的陈述，不是系统自动证明的事实。新增 `supports` 不会自动把目标设为绿色，新增 `contradicts` 也不会自动把目标设为红色。

### 2.3 默认不画全部关联线

**概览态：**只显示主树实线。节点卡片显示“关联 N”，其中 N 是该节点直接关联到未归档节点的有效关系条数，不包含后代的关系。

**选择态：**选中节点后，右侧列出它的全部关联，按方向展示“本节点支持…”或“…支持本节点”。画布只显示与当前节点直接有关、且两端都在当前可见树中的关联虚线，最多 6 条。与当前节点无关的关联线不显示。

排序规则固定：用户当前选中的关系优先，其余按关系 ID 排序。超过 6 条时显示“画布显示 6 / N；其余在侧栏查看”，不暗示只有 6 条存在。侧栏分页，每页 20 条，能访问全部关系。

**目标被折叠/在别的分支：**侧栏仍显示目标标题、归属路径和“定位”按钮；画布不画指向不存在节点的线，也不画指向折叠父节点的假语义线。点击定位才展开目标祖先并定位到目标。保留“返回来源节点”操作。

**清除选择：**隐藏关联虚线，回到主树。

第一版不提供“一键显示全项目全部关联线”。完整性通过列表、查询与导出来保证，不通过把所有边挤在屏幕上来保证。

### 2.4 布局和关系严格解耦

输入布局算法的只有主树节点与 `parent_id`。新增、修改、隐藏跨关系均不得改变任何节点的布局坐标。

布局从左到右，卡片固定 280×144 CSS 像素；标题最多两行，摘要最多两行。长内容进入详情面板。一级路线按固定顺序排列，不按状态、更新时间或关联数自动排序。

推荐用 `d3-hierarchy` 的 `tree().nodeSize([176, 380])` 生成固定尺寸主树布局。D3 的 x/y 需要交换后适配从左到右的画布，并减去半个卡片宽高转换到左上角坐标。节点按 `(order_index, id)` 排序。参数集中为常量，视觉验收后允许统一微调，但不可让 AI 按节点自由写坐标。[S2]

业务字段 `parent_id` 不要机械赋给 React Flow 的 `parentId`。本方案不使用嵌套画布坐标：构造树用于布局后，所有可见卡片都作为平铺的 React Flow 节点，以绝对坐标渲染。

第一版禁止自由拖动节点、更改节点尺寸和固定节点坐标。人工通过“移动归属”和“上移/下移”调整结构；应用负责重新排版。这是为避免重新陷入维护白板坐标的工作，不是禁止人修改路线。

关联线置于卡片后方，使用虚线；标签只在悬停或选择单条关系时显示。无向关系没有箭头，有向关系指向 target。不实现障碍避让引擎，也不承诺任意关联线绝不交叉；通过少量显示和可定位侧栏维持可读性。

### 2.5 “稳定”的具体含义

同样的主树、顺序和折叠状态，坐标应完全相同。修改文字、状态、证据或关联不重新布局。新增/移动节点、改变折叠状态可能移动其他节点，不能声称所有坐标完全不动。

结构重排时维持当前选中节点的屏幕位置，缩放比例不变；没有选择时使用当前视图根作为锚点。只有首次打开、“适应当前图”和用户主动导航允许调整视野。不在每次轮询/更新后执行全图 `fitView()`。

## 3. 页面与交互

### 3.1 只有一个核心页面

顶部：项目选择、搜索、新增一级路线、适应当前图、近期变化、导出、连接信息。  
中间：可缩放、平移的主树画布，带小地图和缩放控件。  
右侧：选中节点的详情与编辑面板。  
第一次打开项目：显示虚拟根和两层节点，其余折叠。

桌面优先，验收视口 1440×900 和 1280×800。窄屏可以显示基础列表，不开发专用移动布局。界面中文或英文（可切换，见 §0.2 与 DECISIONS §16），API 字段英文。

卡片显示：节点类型、状态文字/颜色、标题、短摘要、直接子节点数、直接关联数。不得只靠颜色传递状态。

信息密度（A+B 增补）：默认阅读档为上表全量；zoom 缩小自动降到精简档（标题+状态点/形状+折叠钮）与概览档（色块+状态字形，叠加屏幕空间的路线名/选中浮层），也可锁定档位。开启低干扰后隐藏标签与计数，图例可展开对照。三档不改坐标（§2.5 增补）。

### 3.2 节点的两种展开要分开

“展开子节点”影响地图中可见的路线；“查看详情”打开右侧文字。点详情不应让卡片变成一张几千字的长纸条。

折叠只属于视图，不修改节点内容、状态和 AI 可读取的数据。保存本浏览器的折叠状态、视图根、缩放和平移，不保存任何科学结论到浏览器作为唯一来源。

可以选择“只看这一分支”，并用面包屑返回。分支内的节点仍能在侧栏看到分支外的关联目标。

### 3.3 人工编辑

必须支持：新增一级节点、新增子节点、修改内容与状态、建立/修改/归档关联、移动归属、同级上移/下移、折叠、搜索、查看变更历史。

创建在图上完成（C 批增补）：点「+ 一级路线」/「+ 子节点」/右键新增不开弹窗，而是在画布父节点旁出现一张虚线**草稿卡**，与右侧面板编辑**同一份**草稿会话。保存前不产生任何请求；请求身份（request_id）在会话内固定，保存失败、断网或版本冲突时草稿原样保留，重试至多产生一条提交；取消则整张卡消失、不留记录。切换布局草稿不丢，大纲模式降档为只读虚线行；正在编辑草稿的既有节点卡片带「未保存」标记。CreateNodeModal 类弹窗不再存在。

修改使用明确的“保存/取消”，不在每次输入字符时写数据库。未保存时切换节点必须提醒；服务器有新版本时保留本地草稿，不自动覆盖。

新增关联使用“选择目标 → 选择类型 → 填一句原因”。第一版可不提供拖拽连线，防止把一次拖线误当成主树移动或科学判断。

第一版不硬删除节点。有误建节点可归档并写原因。为了避免隐藏整条仍有效的路线，只允许归档没有子节点的叶子；有子节点时提示先移动或处理子节点，禁止自动级联删除。归档不等于失败。

红色节点仍留在原位，也可以继续有子节点，例如改进版或反例解释。父子状态不自动传播；关闭一条具体尝试，不自动判死整个上位方向。

### 3.4 搜索与定位

支持中文子串与英文不区分大小写的关键词搜索，搜索标题、摘要、标签、观察和结论。不要用仅适配英文分词的实现冒充中文可用。

搜索在列表中显示路径和状态，不先隐藏整张主树。点击结果展开必要祖先并定位节点。不能因为某节点已折叠就搜不到。

节点提供可复制深链接，例如 `/p/<project_uuid>?node=<node_uuid>`。链接不携带访问令牌。刷新或新设备打开后，登录并恢复到对应节点。

### 3.5 AI 更新后的提醒

浏览器每 20 秒读取项目 revision，页面重新获得焦点时也检查；提供手动刷新。只提示“有新的记录”，不自动重排用户正在阅读的地图。

用户点击“载入更新”后读取最新数据，标记新增/修改的节点。若改动藏在折叠分支里，其最近可见祖先显示“分支内有更新”。顶部“近期变化”可以定位到具体节点。

节点历史可查看旧版字段并复制；不做全局一键时间旅行。纠错通过新提交进行，旧记录不抹掉。

## 4. 记录内容与科研边界

### 4.1 一个节点是一个有独立意义的研究单元

可以是问题、想法、关键尝试或发现；不要求每条路线机械套成同一套节点链。

只有当一次工作产生了独立的问题、明显不同的方法、可复用的发现或影响下一步的决策，才新建节点。相同方法的一组参数扫描，通常更新一个节点并附引用，不按每个运行编号无限拆分。

### 4.2 两级文字，外加证据引用

主图的 `summary` 是一句话研究增量，不是操作流水账。

详情面板提供四个短字段：
- `rationale`：为什么做，试法是什么。
- `finding`：直接观察到了什么，尚未确认时写未知。
- `decision`：当前解释与下一步决定，明确哪些是推断。
- `scope`：结论适用的模型、任务、训练/推理条件或尚缺哪些条件。

还可展开 `details_md` 查看长说明。可附外部日志/报告路径或链接，但第一版不接管实验文件、训练权重和图表存储。

### 4.3 状态

| 值 | 显示 | 含义 |
| --- | --- | --- |
| `unexplored` | 灰：未探索 | 想法或问题尚未验证 |
| `in_progress` | 蓝：进行中 | 正在进行有效探索 |
| `promising` | 青：有积极迹象 | 有继续探索价值，但证据还不足 |
| `supported` | 绿：当前条件下支持 | 有证据支持本节点表述的有限结论 |
| `not_supported` | 红：当前条件下不支持 | 当前测试未支持具体方案/假设，不是永久证伪 |
| `inconclusive` | 黄：尚不能判断 | 证据不足、互相冲突或实验本身无效 |

红和绿都要求填写 `scope`、`finding`、`decision`，并至少有一条证据引用。后端校验非空；UI 提醒这些只是记录完整性要求，不是自动科学审查。

代码出错、环境异常、指标缺失通常记为 `inconclusive`，原因写在观察/结论中。不要因此把想法标红。积极但初步的现象用 `promising`，不要靠绿色暗示已普遍验证。

例如，“这次配置下没有改善；只测试了模型 X 和固定预算 Y”是合格的负结果；“此方向永远无效”不能从一次失败推出。

## 5. 最小数据模型

只需要四类业务数据：Project、Node、Relation、Commit。证据嵌在 Node 中；不单独建设 Experiment 平台。数据库中的技术迁移表不算新增产品模块。

### 5.1 Project

`id: UUID`、`name`（1–100 字符）、`objective`（1–4000 字符）、`revision: integer >= 0`、`created_at`、`updated_at`、`created_by`。时间由服务器生成并以 UTC 存储，UI 本地化显示。

项目创建后 revision 为 0。可以更新名称与目标，第一版不删除项目。

### 5.2 Node

| 字段 | 约束 / 默认 |
| --- | --- |
| `id` | UUID，客户端生成，创建后不可修改 |
| `project_id` | 路由确定，不允许客户端跨项目写入 |
| `parent_id` | 同项目 Node UUID 或 null |
| `order_index` | 同级顺序，服务器管理 |
| `kind` | `question` / `idea` / `attempt` / `finding`，默认 idea |
| `title` | 1–80 字符 |
| `summary` | 0–280 字符 |
| `status` | 上述六种，默认 unexplored |
| `rationale` / `finding` / `decision` | 分别 0–2000 字符 |
| `scope` | 0–1000 字符 |
| `details_md` | 0–30000 字符 |
| `tags` | 最多 10 个，每个 1–32 字符，去重 |
| `evidence` | 最多 20 条，默认空数组 |
| `archived` | 默认 false；归档通过专门操作 |
| `created_at` / `updated_at` | 服务器时间 |
| `created_by` / `updated_by` | 服务器根据认证令牌确定 |

证据项只有：`kind: inline|url|path`、`label`（1–120）、`value`（1–4000）、`note`（0–500）。

- inline：在系统中保存的一小段原始观察或人工说明；必须如实说明来源，不充当虚构的外部实验。
- url：外部 http/https 地址。
- path：服务器/本机报告路径，作为可复制定位信息，不代表网页有权限读取该文件。

系统不自动抓取证据、不运行路径里的命令、不代理服务器任意文件、不假装已校验证据真实性。示例数据必须明确标记为合成案例。

**没有 x、y、width、height、pinned 字段；AI 无权提交这些布局参数。**

### 5.3 Relation

`id: UUID`、`project_id`、`source_id`、`target_id`、`kind`、`reason`（1–500）、`archived`、创建/更新时间与作者。

端点创建后不可修改；改错端点用归档旧关系并创建新关系，历史可见。`kind` 和 reason 可更新，但仍须检查重复关系。归档重复关系不允许通过 create 静默覆盖；应该显式 restore 再修改。

### 5.4 Commit

`id: UUID`、`project_id`、`request_id: UUID`、`request_hash`、`base_revision`、`revision`、`actor`、`client_label`（可选、自报名称，不作为权限身份）、`summary`、`operations_json`、`changes_json`、`response_json`、`created_at`。

`changes_json` 存本次所有受影响对象的 before/after（包括服务器调整的顺序）；用于审计与历史展示，不要求实现完整事件溯源系统。

约束：`(project_id, revision)` 唯一；`(project_id, request_id)` 唯一。项目创建请求的幂等信息可以单独存于 Project 的技术字段，不增加用户可见概念。

`Node`、`Relation` 的结构不带当前用户的折叠/选择/视野。业务内容、修改历史、浏览视图是三种不同信息，不能混在一起。

## 6. 写入协议：一次提交一个小变化，而不是覆盖全图

浏览器编辑和 AI 写入必须调用同一套后端业务逻辑。浏览器的一次保存可以只有一条操作；AI 的一次研究增量可以有多条操作。

统一请求形状：

```json
{
  "request_id": "<UUID>",
  "expected_revision": 12,
  "summary": "补充停止条件的负结果，并登记一个待验证变体",
  "client_label": "optional-agent-label",
  "operations": []
}
```

`summary` 为 1–500 字符。operations 为 1–100 条，请求体上限 2 MiB。所有 JSON 模型拒绝未知字段，避免 AI 输入“x/y”或拼错字段却被静默忽略。

### 6.1 支持的操作

| op | 必要参数与语义 |
| --- | --- |
| `project.update` | `fields` 仅允许 name、objective |
| `node.create` | `id`、`parent_id`、`title`，其余内容字段可选；可选 after_id |
| `node.update` | `id`、`fields`；只能改 kind、title、summary、status、四个短字段、details_md、tags、evidence |
| `node.move` | `id`、`parent_id`；可选 after_id，不能导致主树成环 |
| `node.archive` | `id`、`reason`；仅允许叶节点 |
| `node.restore` | `id`、`reason`；父节点必须有效 |
| `relation.create` | `id`、`source_id`、`target_id`、`kind`、`reason` |
| `relation.update` | `id`、`fields`；只改 kind、reason |
| `relation.archive` | `id`、`reason` |
| `relation.restore` | `id`、`reason`；两端必须未归档 |

创建和移动时，after_id 缺省表示追加到同级最后；显式 null 表示最前；UUID 表示放到该有效同级节点之后。不能指定自己。服务器负责生成/重排 order_index。

操作按列表顺序执行，新父节点必须在子节点之前创建，关系放在端点之后创建。每步遵守引用约束；一批任意一步失败都整体回滚。客户端生成 UUID 以便一批中相互引用，不需要额外的临时 ID 协议。

update 是局部字段更新：未提供的字段保持不变；清空字符串用 `""`、清空数组用 `[]`，不要把缺省字段当作空值覆盖。不得修改服务器作者、时间、项目归属、坐标或 revision。

归档节点时，相关关系仍留存，但正常图和普通关联计数不渲染这些关系；历史中可以查看。恢复节点后，两端有效且自身未归档的关系重新可见。

### 6.2 必须有的四项保护

**事务。** 节点、关系、顺序、项目 revision 和 Commit 必须在同一数据库事务中完成。不能写完一半就让人看到断裂地图。

**版本检查。** 写事务内比较 expected_revision 与数据库 revision；不一致返回 409 `REVISION_CONFLICT` 和 current_revision。不以“后写覆盖先写”处理。v0.1 使用整个项目的 revision，宁可让不相关的并发编辑偶尔冲突，也不做复杂自动合并。

**幂等。** 同一项目同一 request_id、相同规范化请求内容重试，返回原响应，不增加节点或 revision。必须先检查已成功提交的 request_id，再比较 expected_revision，否则网络重试会错误冲突。同一个 request_id 用于不同内容，返回 409 `IDEMPOTENCY_KEY_REUSED`。

**可追溯。** 每次成功提交 revision 加 1，记录 actor、原因及前后变化；失败不产生一半成功的 Commit。

事务可使用 SQLite 的短写事务与适当 busy_timeout；版本判断、幂等判断与真实写入必须处在同一串行化写入边界内，不能只在事务之前检查。

### 6.3 预检查

`POST .../commits?dry_run=true` 验证并返回计划变更、警告和当前 revision，不持久化任何节点、顺序、历史、幂等键或 revision。

正式提交仍需重新校验，预检查不是锁，不保证之后没有人修改。对相同已成功提交的请求，可返回原提交信息和 `already_committed: true`，但仍不得重复修改。

### 6.4 错误与成功返回

成功至少返回 `commit_id`、`request_id`、`revision`、新增节点 ID、修改节点 ID、关系 ID、warnings。revision 是这次提交的版本，不冒充查询时最新版本。

错误统一为 `{ "error": { "code": "...", "message": "...", "details": {...} } }`。必要时标出 `operation_index` 和字段路径。

必须区分 401 无效认证、404 不存在/不属于当前项目、409 版本或重复键冲突、413 请求过大、422 内容/结构无效、503 数据库繁忙可重试。客户端保留原请求 ID 重试瞬时网络错误，但禁止悄悄提高 expected_revision 或自动改研究结论以绕过冲突。

## 7. API 与 AI 使用入口

基础路径 `/api/v1`。除最小健康检查与静态前端壳以外，项目数据、导出和接口 schema 都要求认证。404 不能返回整个单页应用 HTML。

### 7.1 端点

| 方法与路径 | 用途 |
| --- | --- |
| `POST /projects` | 创建项目；body 包含 request_id、name、objective，返回 id 与 revision=0 |
| `GET /projects` | 列出项目，默认最多 50，支持分页 |
| `GET /projects/{p}` | 名称、目标、revision、基础数量 |
| `GET /projects/{p}/graph` | 图的轻量元数据，不包含 details_md 和完整证据 |
| `GET /projects/{p}/nodes/{n}` | 节点完整内容与明确的 project_revision |
| `GET /projects/{p}/nodes/{n}/relations` | 全部直接关联及目标路径，分页；可要求查看归档 |
| `GET /projects/{p}/search?q=...` | 分页关键词搜索，默认返回未归档节点 |
| `GET /projects/{p}/context` | 项目/局部上下文，见下一节 |
| `GET /projects/{p}/commits` | 分页变更历史，支持 after_revision 与 node_id |
| `GET /projects/{p}/commits/{c}` | 单次提交详情与 before/after |
| `POST /projects/{p}/commits` | 统一写入；支持 dry_run |
| `GET /projects/{p}/export` | 完整逻辑 JSON 导出，含归档记录和历史 |

所有读取结果应明确对应哪个 revision。一次 context/graph/export 中的数据从同一个一致读取快照获取，不把几次不同版本查询拼在一起。

项目创建本身也需幂等：同一认证主体重复提交相同 request_id 和相同内容，返回原项目；不同内容则 409。实现可以在 Project 保存 create_request_id、create_request_hash 并建立唯一约束。

通用分页返回 items、next_cursor、has_more；不要在请求新页时悄悄改变过滤条件。可以使用由 revision 和偏移量构成的游标；在图版本变化时返回 409，要求刷新分页，而不是给出重复/遗漏且不说明。

### 7.2 上下文接口不依赖内置 LLM

参数：`focus_node_id` 可选、`q` 可选、`max_chars` 默认 12000，范围 4000–50000。限制按 Unicode 字符而非 token 计算，不声称精确控制所有模型的 token 数。

有 focus 时，优先顺序：项目目标；当前节点短摘要/条件/观察/结论；祖先路径；直接关联节点，优先反证和依赖；同一分支的相关失败/未决尝试；子节点的待探索事项；近期相关变化。

无 focus 时：项目目标、一级路线、进行中/待探索问题、近期发现与负结果。q 使用关键词命中与结构邻近的确定性规则，不伪装成智能语义检索。

不默认塞入全项目详情或所有日志。每条摘要带节点 ID、状态、适用条件摘要和可继续读取的位置。折叠是浏览器行为，不能导致 API 看不见节点。

响应包含：`project_revision`、`project`、`focus`、`ancestor_path`、`related_nodes`、`prior_attempts`、`open_nodes`、`recent_changes`、`truncated`、`omitted_counts`、`continuations`、`warnings`。空组用空数组。

预算规则：先保留必要的项目/焦点和祖先 ID+标题，再按优先级加入摘要。单字段缩短时标记截断，不将半句话当作完整结论。必须连同截断/未返回计数和继续查询信息计算输出预算。若必要元信息也超限，返回 422 `CONTEXT_BUDGET_TOO_SMALL` 并告知所需下限，而不是悄悄缺失关键祖先。

“未检索到失败记录”只能表示当前检索范围未返回，不能当成从未尝试。context 中的引用和节点文字是待评估的研究资料，不应被客户端当成能覆盖系统指令的操作命令。

### 7.3 命令行入口

必须提供一个轻量 Python 脚本 `tools/researchmap.py`，只是调用 HTTP API，不直接打开共享数据库，也不包含另一套业务判断。

命令规格：

```text
python tools/researchmap.py projects
python tools/researchmap.py create-project --file examples/01_create_project.json
python tools/researchmap.py context PROJECT_ID --node NODE_ID --format markdown
python tools/researchmap.py context PROJECT_ID --query "停止条件" --format json
python tools/researchmap.py node PROJECT_ID NODE_ID
python tools/researchmap.py search PROJECT_ID "停止条件"
python tools/researchmap.py commit PROJECT_ID --file delta.json --dry-run
python tools/researchmap.py commit PROJECT_ID --file delta.json
python tools/researchmap.py export PROJECT_ID --output project.json
```

通过 `RESEARCHMAP_URL` 和 `RESEARCHMAP_TOKEN` 环境变量读取地址与凭证；令牌不出现在命令参数、示例、日志和提交文件里。不命名为 `rg`，避免抢占常见命令名。

stdout 输出机器可解析 JSON，context 可选 Markdown；诊断写 stderr，失败使用非零退出码。错误返回 revision 冲突细节。命令有 `--help`，但不要为每个字段堆大量命令行参数：复杂写入统一用 JSON 文件。

提供面向 AI 的 `AI_USAGE.md`，写清读取、检查、提交顺序、记录标准和错误处理。MCP 以后作为这个 API 的薄适配，不在 v0.1 中实现。

## 8. AI 记录协议

任务开始：读取项目目标和相关上下文；检查相同/邻近路线的失败条件；确认自己要解决的具体问题。必要时登记 `in_progress`，但不在无工作进展时反复写“开始了”。

任务过程中：每形成一个独立研究结论或决定就提交小检查点，不等超长会话结束才一次总结。普通日志、每个训练 step 和无信息增量的重复运行不生成节点。

方法或适用条件发生实质变化时，应创建变体/新尝试节点并关联，保留原尝试的失败条件；不能把旧方法直接改名并标绿，抹去演化原因。纠正数据错误可修改原节点，但要写明理由。

任务结束：把直接观察与机制解释分开；相同尝试更新原节点，独立新方向创建节点；填条件与证据定位；判断是支持、不支持、初步有望还是未知；补上与其他分支的明确关联原因；dry-run 后正式提交。

未完成、程序出错、证据缺失就如实写，不为了让图“闭环”虚构结果。不因单次失败自动关闭上位方向，不为了避免冲突覆盖人工备注，不修改无关分支。认为既有记录有误时，以带理由的新修订纠正，保留历史。

第一次迁移旧项目时，不从记忆编造实验版本、数字、日志路径或“已验证”。有来源的内容导入为有来源记录，来源不足则标注“历史回忆，待核实”，使用 inconclusive 或 unexplored。

v0.1 不强制审核所有 AI 提交，避免新增一整套审批系统；但每次变更必须留作者与理由，UI 必须可查看和纠正。信任边界是本人和本人授权的工具，不适合未经信任的第三方写入。

## 9. 技术与部署决定

前端固定为 React + TypeScript + Vite + `@xyflow/react` + `d3-hierarchy`。React Flow 提供画布交互和自定义节点；布局是独立模块，不是库自动保证的视觉效果。[S1][S2]

后端固定为 Python + FastAPI + Pydantic + SQLAlchemy，SQLite 持久化，使用简洁的 schema 迁移。FastAPI 的 OpenAPI/JSON Schema 支持用于生成接口说明，后端 schema 是 API 合同的权威来源；前端必须校验类型一致，避免重复定义后漂移。[S3]

第一版不引入 ELK、Dagre、力导向算法、Neo4j、Redis、消息队列或服务网格。选择固定卡片主树布局后，不需要完整通用图布局引擎。未来发现主树不够表达导航时再评价更复杂布局。

生产构建采用多阶段 Docker：构建前端静态资源，复制给 FastAPI 同源提供；运行时一个应用容器、一个 API 进程、一个本地持久卷。开发时可以分别启动 Vite 和 API；生产时不跑 Vite 开发服务器。

开发 AI 应在实现时查阅所选库的官方当前文档，解析互相兼容的版本并生成依赖锁文件，不凭本规格假造版本号，不依赖收费示例代码才能完成核心功能。

### 数据库运行边界

开启 SQLite 外键和 WAL，设置有限 busy_timeout，写事务保持短小，不在事务内执行网络请求或 LLM 推理。数据库只位于部署主机的本地文件系统持久卷，不能放在实验室 NFS/SMB 共享盘让多台机器直接读写；SQLite WAL 的共享内存约束不支持这种网络文件系统用法。[S4]

服务器上的 AI 也必须调用 API，不允许绕过 API 直接改数据库。第一版不承诺高频并行写入，多个 AI 的短增量通过事务和冲突检测协调。

### 访问与安全

默认 Docker 发布到宿主机 `127.0.0.1:8000`，不要默认 `0.0.0.0` 裸露公网。远程访问由部署者在私有网络或已有 HTTPS 反向代理中提供；不改已有 SSH、防火墙、Tunnel 或其他服务配置。

应用级 Bearer Token 必须启用。使用一个研究者令牌和若干具名 AI 令牌，均属同一个受信任空间；令牌哈希与名称放在受保护配置中，不做注册/组织/细粒度权限。作者身份取自认证，不信任请求 body 的 actor。[S5]

前端提供简单的访问令牌输入，令牌只存页面内存，刷新需要重新输入，v0.1 不做浏览器持久化登录。无认证 Cookie，跨域默认拒绝；凭证不得放 URL、localStorage、导出文件或 Git。通过 HTTPS 或受保护的隧道传输，不发送裸公网 HTTP 令牌。

Markdown 禁用原始 HTML 和脚本，只允许安全链接；禁用自动加载外部图片和链接预览，避免内容成为网络探测入口。受管图片附件（§9.1）只经认证字节流加载，外链 `https://` 图片一律降为占位条、永不发起请求。path 引用只显示/复制，不提供任意文件读取接口。API schema 和导出也要认证，前端不记录凭证。使用参数化 SQL，限制输入大小，错误响应不泄露密钥或栈中的私有路径。

### 备份、导出与恢复

必须提供完整项目 JSON 导出，包含 schema_version=2、导出时 revision、节点、关系、历史和附件元数据（id/mime/sha256/尺寸等；**图片字节不入 JSON**，随备份包走）。它是便携数据档案，不宣称 v0.1 已支持任意 JSON 合并导入。

必须提供离线管理命令进行数据库快照备份，调用 SQLite 在线备份能力生成一致快照。不能在运行中仅复制 `.db` 并假设 WAL 中的修改都已经包含。[S6]

备份不含访问令牌配置，也不包含 evidence 指向的外部文件。附件字节目录（`RESEARCHMAP_STORAGE`，默认与库同卷）随备份命令拷入 `<out>/attachments/` 并生成逐文件 sha256 manifest（缺失/损坏只记账不中断；恢复后核对库内元数据与目录覆盖）。文档说明应将快照复制到另一存储位置。恢复时先停止应用，保留当前数据的备份，恢复已验证快照，再启动并检查节点、关系、历史数量和深链接。不能在应用运行时直接覆盖 SQLite 文件。

重建容器、重启应用和 schema 迁移不能默认清空用户数据。示例 seed 必须显式执行，不自动写进真实项目。

### 9.1 受管图片附件

正文以纯 Markdown 源引用附件（`![alt](attachment:<uuid>)`），复制/导出/搜索全部可用。上传走 `POST /api/v1/projects/{pid}/attachments`（multipart，单文件 ≤10MB、Pillow 探尺寸 ≤8000px、必须 image/*），入库为 `staged`；提交事务内扫描 node.create/node.update 的 details_md 与 evidence 引用，同事务翻转为 `attached`。`GET /api/v1/attachments/{id}` 经认证供给字节流（ETag=sha256）；`GET /api/v1/projects/{pid}/attachments` 列元数据。attached 永不删（替换=新 id），staged 且无引用超 30 天在上传事务顺带清理。字节落 `RESEARCHMAP_STORAGE`（默认 `<db dir>/attachments`）。

## 10. 验收测试：这些比“页面能打开”更重要

测试数据使用合成科研案例，不将演示结论混入用户真实项目。至少准备普通案例和大图案例；后者目标为 1000 节点、3000 关联，通常只展开不超过 300 张卡片。规模是验收场景，不是未测量的性能保证。

| 编号 | 操作 / 条件 | 必须满足 |
| --- | --- | --- |
| T01 | 空项目新增两条路线与子节点 | 保存、刷新、重启后内容一致 |
| T02 | 相同主树重复布局 3 次 | 坐标相同，卡片不重叠 |
| T03 | 新增 30 条跨分支关系 | 主树所有坐标不变；默认无满屏关联线 |
| T04 | 修改标题、摘要、状态和长详情 | 坐标不变，卡片尺寸不变 |
| T05 | 折叠分支后查询 API 和搜索后代 | 数据仍完整；定位可展开祖先 |
| T06 | 关联端点被折叠/在其他视图根外 | 侧栏可查路径和定位；没有指向假端点的线 |
| T07 | 单节点超过 6 条关联 | 画布有上限与提示，列表能访问全部 |
| T08 | 父节点标红，子节点标绿 | 两者状态都保留，不剪枝、不传播否定 |
| T09 | 程序出错的案例 | 标为尚不能判断；没有自动全局证伪 |
| T10 | 设置红/绿但无 scope 或证据 | 422 并指出缺失项；已有草稿不丢失 |
| T11 | 一批中创建节点后创建合法关系 | 原子成功，只增一个 revision |
| T12 | 批中最后一步端点非法 | 整批回滚，所有对象与 revision 不变 |
| T13 | 对同一成功请求重复提交 | 返回原结果，不多写一次 |
| T14 | 同 request_id 改内容再次提交 | 409，拒绝复用 |
| T15 | 两个客户端从同一 revision 写入 | 一个成功，另一个 409；没有静默覆盖 |
| T16 | dry-run 然后刷新数据库 | 没有任何持久变化；正式提交重新校验 |
| T17 | 主树移动到自己的后代；跨关系构成环 | 前者拒绝，后者可合法保存 |
| T18 | 跨项目父节点/关联；自关联；重复 related 反向提交 | 拒绝，不污染其他项目 |
| T19 | API 收到 x/y、未知状态或拼错字段 | 422，不静默接受 |
| T20 | 归档有子节点的节点 | 拒绝并给出处理路径；没有级联删除 |
| T21 | 重新打开深链接 | 正确项目、节点和祖先展开，无令牌泄露 |
| T22 | UI 有未保存草稿，此时 AI 更新 | 草稿保留，有冲突提示，不擅自覆盖 |
| T23 | context 达到字符预算，包含折叠失败节点 | 预算可检查；截断和未返回项明确，可继续读取 |
| T24 | 无令牌读取图/导出/写入；危险 Markdown/path | 认证拒绝；不执行脚本、不抓取任意路径 |
| T25 | 重建容器和快照恢复 | 数据、关系、历史可恢复；外部证据文件不被谎称已备份 |
| T26 | CLI 新 AI 接手、读取局部、提交、重试 | 能完成闭环，错误可机器解析，不要求模型 API Key |
| T27 | 大图、两种桌面视口、长中文和多关联 | 概览不全展开；标题可读、侧栏可用，不被大量线遮蔽 |

测试分工：后端自动化覆盖事务、状态校验、幂等、冲突和权限；前端单元测试覆盖布局确定性、可见集和关联显示规则；浏览器端到端测试覆盖编辑、刷新、搜索定位、折叠和跨关系。

大图测试必须记录实际硬件、浏览器、可见节点数、首次布局耗时和交互表现。无法在环境中执行的项目应写“未验证”，不能把编译通过当成交互验收通过。

## 11. 开发顺序与交付

### 阶段 A：先验证主树是否真正好读

使用合成数据完成固定卡片布局、折叠、详情、关联计数、最多 6 条按需关联、定位与视图锚定。此阶段允许内存数据，但不是最终交付。用含红节点继续分叉和多关联的复杂案例验收，而非只有三个节点的截图。

### 阶段 B：接入可持久化记录

实现四类数据、同一写入服务、人工编辑、验证、历史、幂等与 revision 冲突。停止使用前端静态 JSON 冒充数据库。完成重启恢复与错误回滚测试。

### 阶段 C：接入外部 AI

实现 context、搜索、批量提交、dry-run、CLI、AI_USAGE.md 和示例。用一段独立终端会话模拟新 AI，不依赖当前开发对话的隐含上下文。

### 阶段 D：服务器与端到端交付

完成单容器构建、认证、持久卷、导出、备份恢复、合成大图和浏览器测试。记录限制，不扩建平台。

阶段顺序不代表允许跳过后面内容；v0.1 完整交付应完成全部必须项。若因工具/环境限制未完成，需要明确列出，不以“基础架构已就绪”代替真实验证。

建议代码目录：

```text
researchmap/
  frontend/               # 地图、详情、布局纯函数、浏览器测试
  backend/                # 模型、API、服务层、迁移、后端测试
  tools/researchmap.py    # 仅 HTTP 的薄 CLI
  tools/backup.py         # 仅供部署管理员使用
  examples/               # 显式标记 synthetic 的请求与测试数据
  docs/SPEC.md
  docs/AI_USAGE.md
  docs/DECISIONS.md       # 少量工程选择，不记录逐行开发流水账
  Dockerfile
  compose.yaml
  .env.example           # 只包含占位符，不含真实令牌
  README.md
```

最终交付必须给出：实际可运行代码、依赖锁文件、构建/启动步骤、认证配置、数据存放位置、CLI 示例、测试执行结果、备份恢复步骤、尚未完成清单。不得提交密钥、实验室真实数据或用户私有报告。

## 13. 最后检查

不要交付一个“任何图都能画”的软件，而要交付一个“科研记录持续增加，仍能读懂”的软件。完整保存关系，不等于同时显示所有线；记录失败，不等于把一次失败提升为永久定论；服务于 AI，不等于必须内置 AI。
